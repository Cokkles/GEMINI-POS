# GPOS Android 0.1 — Authentication & Backend Connectivity Readiness

Status: read-only reconnaissance; no shared auth/backend change authorized by this document.

## Objective

The 0.1.x phase should make Android an authenticated direct consumer of versioned shared GPOS read contracts without depending on Desktop, the Windows Helper, loopback APIs, helper cookies or helper-local session tokens.

## Current AUTH-1 production state

Repository evidence is now reconciled against commit chronology.

`docs/security/AUTH-1-STATUS.md` is an older integration-status record from August 23 that says production enforcement was still pending. The newer `docs/security/AEGIS-AUTH-PHASE-A1-CUTOVER.md`, updated August 27, records AUTH-1 as COMPLETE / PRODUCTION VALIDATED on backend 2.6.0 with `AEGIS_AUTH_REQUIRED=true`.

For Android 0.1 planning, the newer cutover record is authoritative unless live production inspection proves otherwise.

The production cutover record establishes:

- Google Identity Services + server-side allowlist are active AUTH-1 identity controls;
- `AEGIS_GOOGLE_CLIENT_ID` is the PWA Web client audience;
- `AEGIS_GOOGLE_CLIENT_IDS` supports additional explicitly trusted audiences, including the Desktop Helper client;
- `AEGIS_AUTH_ALLOWED_EMAILS` remains private in Apps Script Script Properties;
- public `auth_config` remains available;
- protected Workspace-backed reads are authenticated POST actions rather than private GET routes;
- clients attach a Google ID token as `auth_token` to protected POST operations;
- rejected/expired identity returns the client to the secure access boundary.

## AUTH-1 implementation evidence

Read-only inspection of `Cokkles/aegis-itinerary-project/apps-script/AEGIS_AUTH1_Code.gs` shows the validation semantics used by the AUTH-1 candidate lineage:

- trusted OAuth audiences are read from `AEGIS_GOOGLE_CLIENT_ID` plus optional comma-separated `AEGIS_GOOGLE_CLIENT_IDS`;
- authorization uses `AEGIS_AUTH_ALLOWED_EMAILS`;
- Google ID tokens are validated server-side;
- token audience must be in the trusted-client set;
- email must be verified;
- token must be unexpired;
- issuer must be Google when present;
- email must be on the AEGIS allowlist.

The source file still contains historical staging commentary, so deployment state should be taken from the newer production cutover record rather than that comment.

## Production protected-read mapping

The cutover record documents these AUTH-1 POST actions:

- `getHorizonData` / `getSummary` -> `get_dashboard`
- `getIntelligence` -> `get_intelligence`
- `capabilities` -> `get_capabilities`
- `getNotifications` -> `get_notifications`
- `getRecentFinance` -> `get_recent_finance`
- `health` -> `get_health`
- `getLatestHorizonBriefing` -> `get_latest_horizon`

This is the strongest current candidate for Android 0.1 read-only transport discovery. Android must still confirm the exact request/response envelope before implementation.

## Desktop/Helper mechanisms that Android must NOT reuse

The Helper API is intentionally local and Windows-oriented:

- loopback base URL (`127.0.0.1` / localhost)
- `gpos_session` cookie / `X-GPOS-Session` local helper session
- helper process instance identity
- local browser callback lifecycle
- helper-local credential custody and revocation
- Host-header loopback enforcement and PWA-origin policy

Those are Desktop/PWA bridge implementation details, not a portable GPOS authentication protocol for Android.

## Semantics Android can reuse

Android 0.1 should reuse or remain compatible with:

- AUTH-1 Google ID-token identity semantics;
- existing server-side email allowlist behavior;
- explicitly trusted OAuth audiences;
- verified-email, expiry and issuer validation;
- authenticated protected POST actions;
- finite authentication failure categories where applicable;
- native/system-mediated Google authentication rather than embedded WebView auth;
- PKCE when an authorization-code public-client exchange is used;
- bounded timeouts and finite retry behavior;
- typed read operations and explicit capability/version negotiation;
- no automatic mutation retry;
- safe auth diagnostics that expose state but never credentials;
- explicit sign-out/re-authentication state transitions.

## Required Android OAuth decision

Android needs its own native Google OAuth client registration. Production AUTH-1 already supports an additional trusted-audience list, so the preferred compatibility path is additive: register the Android OAuth client and add its audience to the existing trusted set without changing the PWA client ID or Desktop Helper audience.

That production trusted-audience configuration is a cross-client security change and must be explicitly reviewed before it is made.

Do not hard-code a client ID, redirect URI, scopes or audience until the Android OAuth registration is approved. Do not place the email allowlist in the Android repository or package.

## Proposed 0.1 implementation sequence

### 0.1-A — Contract discovery

- Confirm live/public `auth_config` semantics against backend 2.6.0.
- Inspect the current authenticated POST envelope used by `auth_login`, `auth_session`, and protected read actions.
- Inspect concrete response schemas for `get_dashboard`, `get_capabilities`, `get_health`, `get_latest_horizon`, `get_notifications`, and `get_recent_finance`.
- Define Android-supported capability/contract versions from actual responses rather than inventing identifiers.
- Identify the minimum Android OAuth registration/configuration change needed to join the existing trusted audience set.

### 0.1-B — Native auth plumbing

- Add native/system-mediated Google authentication using the approved Android OAuth registration.
- Use PKCE if the selected flow performs authorization-code exchange.
- Add a concrete Android Keystore-backed `CredentialStore`.
- Keep ID/access/refresh credentials outside Compose UI state and logs.
- Implement explicit Signed Out / Authenticating / Authenticated / Expired / Error UI states.
- Add logout that clears local protected credentials even when remote revocation is unavailable.

### 0.1-C — Read-only HTTP transport

- Add Retrofit + OkHttp through one API boundary.
- Enforce HTTPS, bounded connect/read/call timeouts and response-size policy.
- Attach AUTH-1 `auth_token` only through the transport boundary.
- Send compatibility metadata only when the receiving production contract supports it.
- Map finite backend/auth/network failures into typed Android errors.
- Add correlation/request IDs without logging credentials or private payloads.
- Implement protected canonical reads only.

### 0.1-D — Repository wiring

- Map transport DTOs into canonical Android domain models.
- Persist last-known-good results through Room.
- Surface LIVE / CACHED / STALE / OFFLINE status explicitly.
- Preserve cached data on bounded read failures.
- Reject incompatible response contracts instead of guessing.

### 0.1-E — Validation

- Authenticate on emulator/physical device using the approved Android OAuth registration.
- Validate authenticated health/dashboard reads.
- Validate expiration and re-authentication.
- Validate offline cached behavior after a successful read.
- Confirm Desktop/PWA behavior remains unchanged.
- Confirm Android still exposes no remote mutation command surface.

## Stop conditions

Stop and request cross-client review before any change that would:

- alter existing AUTH-1 token semantics;
- add or change a production trusted OAuth client audience without review;
- change identity allowlist behavior;
- require Desktop/PWA clients to send new mandatory metadata;
- modify existing endpoint response semantics;
- add task/calendar/finance mutations;
- route Android through the Windows Helper;
- add aggressive polling or background generation.

## Current recommendation

Complete A0-E first. Then continue 0.1-A by inspecting the actual authenticated POST envelopes and response schemas on the current AUTH-1 2.6.0 code path. The production documentation now indicates that AUTH-1 itself is live; the remaining Android-specific security decision is the native OAuth client registration and addition of its audience to the existing trusted set.
