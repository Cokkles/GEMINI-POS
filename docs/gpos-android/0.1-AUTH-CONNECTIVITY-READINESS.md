# GPOS Android 0.1 — Authentication & Backend Connectivity Readiness

Status: read-only reconnaissance; no shared auth/backend change authorized by this document.

## Objective

The 0.1.x phase should make Android an authenticated direct consumer of versioned shared GPOS read contracts without depending on Desktop, the Windows Helper, loopback APIs, helper cookies or helper-local session tokens.

## Existing identity semantics to preserve

The current AUTH-1-compatible Helper workstream documents Apps Script AUTH-1 as authoritative upstream. The browser/Helper path ultimately presents a Google ID token in the existing AUTH-1 envelope and applies the current identity allowlist semantics.

Android should preserve those upstream identity and authorization semantics, but it must not copy the Desktop transport/custody mechanism.

## 0.1-A discovery evidence

Read-only inspection of `Cokkles/aegis-itinerary-project/apps-script/AEGIS_AUTH1_Code.gs` found an AUTH-1 staging candidate with these semantics:

- public `auth_config` reports provider `google`, whether a Google OAuth client is configured, whether the email allowlist is configured, whether enforcement is required, `auth_version=AUTH-1`, and backend version metadata;
- trusted OAuth audiences are read from `AEGIS_GOOGLE_CLIENT_ID` plus optional comma-separated `AEGIS_GOOGLE_CLIENT_IDS`;
- identity authorization uses `AEGIS_AUTH_ALLOWED_EMAILS`;
- the candidate validates a Google ID token through Google's token-info endpoint;
- it rejects tokens whose audience is not in the configured trusted-client set;
- it requires verified email, non-expired token, acceptable Google issuer, and an email present in the AEGIS allowlist;
- successful verification returns bounded user identity metadata and token expiry.

This is useful compatibility evidence for an Android native client registration because the candidate already models multiple trusted OAuth client audiences. It does **not** authorize Android to add a new audience or change production auth configuration unilaterally.

The same source explicitly says the repository wrapper is an abbreviated AUTH-1 candidate and that the existing deployed `2.5.1` baseline remains production authority until cutover. Therefore these discovered semantics must be reconciled against the actual deployed AUTH-1 configuration before Android live authentication is enabled.

## Desktop/Helper mechanisms that Android must NOT reuse

The Helper API is intentionally local and Windows-oriented:

- loopback base URL (`127.0.0.1` / localhost)
- `gpos_session` cookie / `X-GPOS-Session` local helper session
- helper process instance identity
- local browser callback lifecycle
- helper-local credential custody and revocation
- Host-header loopback enforcement and PWA-origin policy

Those are Desktop/PWA bridge implementation details, not a portable GPOS authentication protocol for Android.

## Semantics Android can reuse

Android 0.1 should reuse or remain compatible with:

- AUTH-1 identity allowlist behavior
- Google ID-token audience validation against an explicitly trusted client set
- verified-email, expiry and issuer validation
- finite authentication failure categories where applicable
- system-browser authentication rather than embedded WebView auth
- PKCE for a public/native client flow when authorization-code exchange is used
- bounded timeouts and finite retry behavior
- typed read operations and explicit capability/version negotiation
- no automatic mutation retry
- safe auth diagnostics that expose state but never credentials
- explicit sign-out/re-authentication state transitions

## Required 0.1 design decision before implementation

A mobile-appropriate Google/OIDC token-acquisition path must be identified and reviewed. The backend candidate evidence shows that the server ultimately needs a Google ID token whose `aud` is explicitly trusted. Android therefore needs a native OAuth client registration whose audience can be added to the authoritative trusted-client set without weakening existing Desktop/PWA validation.

Do not hard-code a provider client ID, redirect URI, scopes, issuer, identity allowlist, token audience or OAuth-client registration into Android until the actual deployed AUTH-1 configuration has been inspected and the mobile registration/redirect model is approved.

Any required change to Apps Script AUTH-1 validation, accepted token audience, scopes, allowlist policy or response semantics is a cross-client review item and is outside unilateral Android 0.1 implementation.

## Proposed 0.1 implementation sequence

### 0.1-A — Contract discovery

- Reconcile the staging AUTH-1 candidate above with the authoritative deployed 2.5.1 AUTH-1 implementation/configuration.
- Confirm the production request envelope carrying the Google ID token.
- Confirm whether production already supports multiple trusted OAuth audiences or requires an additive compatibility change.
- Identify currently deployable versioned read endpoints or the smallest additive direct-client facade needed by Android.
- Define capability/contract discovery behavior.
- Freeze Android-supported contract version identifiers for the first authenticated build.

### 0.1-B — Native auth plumbing

- Add system-browser/native Google authentication appropriate for Android and the approved OAuth registration.
- Use PKCE for any authorization-code public-client exchange.
- Add a concrete Android Keystore-backed `CredentialStore`.
- Keep ID/access/refresh credentials outside Compose UI state and logs.
- Implement explicit Signed Out / Authenticating / Authenticated / Expired / Error UI states.
- Add logout that clears local protected credentials even when remote revocation is unavailable.

### 0.1-C — Read-only HTTP transport

- Add Retrofit + OkHttp through one API boundary.
- Enforce HTTPS, bounded connect/read/call timeouts and response-size policy.
- Send compatibility metadata such as `client_type=GPOS_ANDROID`, product version and supported contract versions only when the receiving contract supports it.
- Map finite backend/auth/network failures into typed Android errors.
- Add correlation/request IDs without logging private payloads.
- Implement canonical reads only.

### 0.1-D — Repository wiring

- Map transport DTOs into canonical Android domain models.
- Persist last-known-good results through Room.
- Surface LIVE / CACHED / STALE / OFFLINE status explicitly.
- Preserve cached data on bounded read failures.
- Reject incompatible contract versions instead of guessing.

### 0.1-E — Validation

- Authenticate on emulator/physical device using the approved production-like Android OAuth registration.
- Validate authenticated health/dashboard reads.
- Validate expiration and re-authentication.
- Validate offline cached behavior after a successful read.
- Confirm Desktop/PWA behavior remains unchanged.
- Confirm Android still exposes no remote mutation command surface.

## Stop conditions

Stop and request cross-client review before any change that would:

- alter existing AUTH-1 token semantics or required audience;
- add or change a production trusted OAuth client audience without review;
- change identity allowlist behavior;
- require Desktop/PWA clients to send new mandatory metadata;
- modify existing endpoint response semantics;
- add task/calendar/finance mutations;
- route Android through the Windows Helper;
- add aggressive polling or background generation.

## Current recommendation

Do not begin live Android authentication yet. Complete A0-E first, then finish 0.1-A by reconciling the discovered staging AUTH-1 candidate with the authoritative deployed 2.5.1 implementation/configuration. The Helper branch remains useful compatibility evidence, but its local session API is explicitly not the Android backend contract.
