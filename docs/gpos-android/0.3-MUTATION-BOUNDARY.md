# GPOS Android 0.3 — Explicit Mutation Boundary

Status: DESIGN FROZEN FOR IMPLEMENTATION
Branch: `agent/gpos-android-foundation`
Client: `GPOS_ANDROID`

## Governing rule

**READ AUTOMATICALLY. MUTATE EXPLICITLY.**

GPOS Android may refresh canonical state automatically, but it must never silently create, complete, acknowledge, regenerate, or otherwise mutate canonical state.

This phase does not require a shared-backend contract change. It adopts only mutation paths already exercised by the authenticated production AEGIS client.

## Proven production mutation paths

### Google Task completion

Existing production client behavior:

1. User stages one or more task IDs locally.
2. Nothing is written while staging.
3. On explicit sync/apply, the client sends:
   - `action = mark_done`
   - `completedTasks = [task ids]`
   - `message = mark_done:`
4. Backend completes the selected Google Tasks and refreshes canonical dashboard state.

Android policy:

- Task rows may be selected/staged locally.
- Staging is clearly labeled as local/pending.
- A dedicated confirmation/apply action is required before network mutation.
- If the request fails, staged state remains visible and no success is fabricated.
- After success, Android refreshes canonical reads.
- Android must not create Google Tasks silently.

### Calendar event creation

Existing production client behavior is two-step:

1. Explicit user request invokes `resolve_calendar_event` with free-text event input.
2. Backend returns a proposed structured event.
3. Client presents the proposed title/time/location/description.
4. Only after explicit confirmation does the client invoke `create_calendar_event` with the resolved event.

Android policy:

- Natural-language resolution is an explicit foreground action only.
- Resolution may be treated as a proposal; it is never creation.
- The full proposed event must be reviewable before creation.
- Creation requires a second explicit confirmation.
- Cancellation performs no write.
- Failure must not be presented as success.
- After success, Android refreshes canonical schedule/dashboard state.

### Notification acknowledgement

Existing production client supports `ack_notification` with `notificationId`.

Android policy:

- Acknowledgement is permitted only from an explicit in-app action.
- Background notification delivery must not acknowledge server state.
- Deep-link opening must not acknowledge server state.
- Failed acknowledgement remains visibly unacknowledged until canonical refresh proves otherwise.

## Explicitly out of scope for 0.3

- HORIZON generation / `horizon_sync`
- Automatic Gemini invocation during background refresh
- PRISM/RSS refresh work from Android routine sync
- Finance writes
- Grocery/task creation
- Notes/journal/calorie/receipt command dispatch
- Ask AEGIS conversational dispatch
- Follow-up creation or Gmail-derived mutation
- Any new shared backend mutation contract
- Any automatic retry of non-idempotent mutations

## Client-side architecture

Mutation calls are separate from `CanonicalReadClient` and read-only refresh APIs.

Suggested boundary:

```text
Canonical reads
  -> automatic / foreground / WorkManager-safe

Explicit commands
  -> foreground only
  -> user intent required
  -> confirmation where destructive or externally visible
  -> no automatic retry unless an idempotency contract exists
```

No mutation method should be callable from `CanonicalSyncWorker`.

## 0.3 implementation sequence

### 0.3.0 — command transport boundary

- Add an explicit authenticated command client separate from read-only actions.
- Add typed request/response models for:
  - task completion
  - calendar event resolution
  - calendar event creation
  - notification acknowledgement
- Add tests proving automatic/background code cannot access mutation APIs.

### 0.3.1 — Tasks

- Local staging UI.
- Pending count and undo-before-apply.
- Explicit confirmation/apply.
- Success refreshes canonical task state.
- Failure preserves staged selections.

### 0.3.2 — Calendar

- Foreground event text input.
- Explicit Resolve/Preview.
- Structured preview.
- Explicit Add to Calendar confirmation.
- Cancel path with zero mutation.

### 0.3.3 — Notifications

- Explicit acknowledge action.
- No acknowledgement on deep-link/open/background delivery.

### 0.3.4 — hardening

- Mutation diagnostics without logging tokens/private payloads unnecessarily.
- Disable command controls when auth is unavailable.
- Verify no WorkManager path can invoke commands.
- Instrumentation coverage for cancel/no-write and explicit-confirm flows.

## Exit criteria

0.3 is complete only when:

- all automatic refresh paths remain read-only;
- each mutation requires an explicit foreground action;
- calendar creation has a preview + second confirmation;
- task completion preserves pending state on failure;
- notification open/deep-link does not acknowledge automatically;
- lint/unit/instrumentation APK assembly passes;
- deterministic checkpoint signing remains unchanged;
- physical-device validation is recorded separately from CI compilation.
