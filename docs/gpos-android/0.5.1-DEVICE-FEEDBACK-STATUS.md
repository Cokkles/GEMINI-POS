## Device-feedback repairs

0.5.1 is a bounded follow-up to the physical-device 0.5.0 parity test.

- Quote rendering no longer crossfades two independently measured text stacks. The card now uses one content-driven column with explicit spacing so quote and attribution can expand vertically without overlapping.
- Canonical machine tokens used as presentation fallbacks are humanized; e.g. `UNDER_TARGET` renders as `Under target` rather than leaking internal enum formatting.
- Obvious count strings on the parity surface now use clean singular/plural labels rather than `(s)` text.
- Task pending presentation uses user-facing `Pending` wording.

## Google Tasks behavior at this checkpoint

The existing safe completion model is retained:

1. Checking an active canonical Task stages a local protected mutation.
2. The task stays visible as Pending for a five-minute Undo grace period.
3. WorkManager submits due completions with connected-network and battery constraints.
4. A completion is considered CONFIRMED only after a fresh canonical Dashboard/Tasks read shows the task is no longer active.
5. Repeated verification failures produce a durable FAILED receipt and local alert rather than false success.

0.5.1 changes **Sync now** into **Sync & refresh Tasks**. It is available even when no completion is pending. When pressed it force-flushes any explicitly queued completion and then requests a fresh canonical read; with no pending mutations it simply refreshes canonical Google Tasks.

## Shared-backend boundary: generic Task creation

Generic Google Task creation is **not implemented in 0.5.1**.

Repository/contract inspection found production-proven task completion (`mark_done`) and the optional capability-gated task-history/restore contract, but no proven generic create-Task action. The legacy grocery route can insert Google Tasks but is semantically grocery-specific and must not be repurposed for ordinary Tasks.

The next safe parity step requires an additive shared contract, proposed as:

- capability: `ux_contracts.tasks_create_v1: true`
- scope: `tasks.write`
- action: `create_task`
- response contract: `AEGIS_TASK_ACTION_V1`
- explicit foreground submit only
- bounded title/notes/due fields
- client submission/idempotency identifier to reduce duplicate creation risk
- fresh canonical verification after successful creation
- Android must not call the action unless capability discovery advertises it
- existing PWA/Windows behavior must remain backward compatible

This proposal is deliberately not deployed from the Android checkpoint. Shared Apps Script implementation/advertising requires an explicit cross-client review/approval.
