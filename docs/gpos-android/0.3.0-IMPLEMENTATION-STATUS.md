# GPOS Android 0.3.0 — Explicit Mutation Implementation Status

## Checkpoint intent

GPOS Android 0.3.0 is the first Android checkpoint that intentionally exposes a bounded set of canonical write operations.

The governing rule remains:

> **READ AUTOMATICALLY. MUTATE EXPLICITLY.**

Android still does not depend on the Windows application or Windows Helper. All reads and writes use the authenticated canonical AEGIS backend directly.

## Explicit command architecture

Canonical/background reads remain in `AegisBackendClient` and `CanonicalSyncWorker`.

Mutations are deliberately isolated in `AegisCommandClient`.

Important boundaries:

- no generic public `execute(action)` or arbitrary-action command method;
- foreground-only mutation controllers;
- command client is not injected into `CanonicalSyncWorker`;
- OkHttp connection retry is disabled for the mutation client;
- callers must hold a current authenticated credential;
- offline-restored/cached state is never sufficient authority to mutate;
- new mutation types require an explicit code/API review rather than string dispatch.

Current finite command surface:

1. Google Task completion — `mark_done`
2. Calendar text resolution — `resolve_calendar_event`
3. Calendar event creation — `create_calendar_event`
4. Server notification acknowledgement — `ack_notification`

## Tasks — staged explicit completion

Implemented:

- task selection/staging is local-only and side-effect free;
- only backend-provided canonical task IDs are eligible for mutation;
- synthesized UI fallback IDs are display-only and cannot be staged as Google Task identifiers;
- user reviews the staged count before submission;
- user explicitly confirms completion;
- mutation transport does not automatically retry;
- selected IDs remain available when the mutation/verification cannot be confirmed.

### Post-write verification

The production `mark_done` backend catches individual Google Tasks patch exceptions internally. Therefore the Android client does **not** treat a generic command response as proof that each selected task was completed.

After an explicit `mark_done` submission Android performs one fresh authenticated canonical dashboard read and verifies that the selected canonical task IDs are absent.

- verified absent -> clear the confirmed completed IDs and refresh UI;
- still present -> preserve those IDs as staged/unconfirmed and surface an error;
- verification read fails -> do not retry the mutation; preserve staged IDs and report uncertainty.

This is intentionally stricter than assuming a successful HTTP/JSON command response equals successful per-task mutation.

## Calendar — resolve, preview, create

Implemented production-compatible two-step flow:

1. user enters natural-language event text;
2. Android sends `resolve_calendar_event`;
3. backend returns a structured proposed event;
4. Android displays the proposal for review;
5. only a separate explicit **Add to Calendar** action sends `create_calendar_event` using that reviewed proposal.

The app does not silently create an event during resolution.

The proposal contains only reviewed fields used by the current production contract:

- title
- start
- end
- optional location
- optional description

After successful creation Android requests a canonical refresh.

## Notifications — explicit acknowledgement

Implemented:

- acknowledgement is a foreground button action only;
- opening Notifications does not acknowledge anything;
- tapping an Android notification/deep link does not acknowledge anything;
- the mutation accepts only the selected server notification ID;
- server `status: success` for the same ID is required before Android treats the acknowledgement as successful;
- `status: not_found`, mismatched IDs, auth errors, network errors, and malformed responses fail closed.

## Android notification permission hardening

Critical Android notification publishing performs an explicit `POST_NOTIFICATIONS` permission check immediately before `NotificationManagerCompat.notify()` and catches a possible `SecurityException` if permission is revoked between check and dispatch.

No private server message is copied into the lock-screen notification.

## Still explicitly gated

0.3.0 does not expose:

- Google Task creation/editing/deletion;
- Calendar edit/delete;
- finance mutation/import/edit;
- Follow-ups mutation/state changes;
- Ask AEGIS conversational command/query transport;
- HORIZON generation;
- PRISM execution;
- RSS/Intelligence refresh;
- arbitrary command dispatch;
- background mutation.

## Validation status

At the first full 0.3 gate, Kotlin compilation, unit tests, debug APK assembly, and AndroidTest APK assembly completed successfully. Android lint then blocked the release on notification runtime-permission handling.

That permission path has been hardened without adding a lint baseline or suppressing the warning. A fresh full checkpoint run is required before 0.3.0 can be called CI-green or its APK supplied as validated.

Physical-device authenticated mutation tests remain required even after CI passes. CI must never perform production Task, Calendar, or notification mutations.
