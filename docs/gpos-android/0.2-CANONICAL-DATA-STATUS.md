# GPOS Android 0.2 — Canonical Data Integration & Mobile Dashboard

Status: implementation checkpoint in validation

## Objective

Turn the authenticated Android shell into a useful read-oriented GPOS client while preserving canonical backend ownership and the rule:

> READ AUTOMATICALLY. MUTATE EXPLICITLY.

Android 0.2 does not create a second domain engine. It consumes bounded, already-proven response fields and persists last-known-good copies only for offline presentation.

## Proven dashboard fields consumed

The production AEGIS PWA currently renders the canonical dashboard from the following response shape:

- `calendar.today[]`
  - `id` when available
  - `title`
  - `time`
  - `note`
- `calendar.tomorrow[]`
  - same bounded event fields
- `tasks[]`
  - `id`
  - `title`
  - `time`
- `briefing.plain_text`
- `briefing.last_updated`
- `system_metadata.last_updated`
- `system_metadata.horizon_generation.last_success`
- `system_metadata.horizon_generation.mode`

Android ignores unknown response fields. Additive backend fields therefore do not silently change mobile behavior.

## Live surfaces in 0.2

### Home

Uses canonical dashboard data for:

- next today/tomorrow event;
- active task count and first tasks;
- HORIZON last-success metadata;
- briefing availability;
- explicit dashboard provenance.

No fixture data is presented as canonical data.

### Briefing

Uses the canonical `get_latest_horizon` read with the dashboard briefing payload as a bounded fallback. Markdown is parsed only for display structure:

- document title;
- `##` sections;
- `###` / `####` subsections;
- presentation-markup stripping.

Android does not infer new task/calendar/domain state from briefing prose.

### Calendar

Read-only rendering of canonical `today` and `tomorrow` event arrays.

### Tasks

Read-only rendering of canonical active task rows.

Task completion/editing remains disabled.

## Still gated

The following surfaces remain explicit placeholders rather than fabricated fixture data:

- Follow-ups — bounded canonical feed not yet proven.
- Finances — must come from SENTINEL-FIN authority through a dedicated read contract.
- Ask AEGIS — model invocation/cost/confirmation contract not yet enabled.
- Calendar mutations.
- Task mutations.

## Cache policy

Two independent Room cache records are used.

### Dashboard

- cache key: `dashboard_v1`
- contract marker: `AUTH-1/get_dashboard/pwa-bounded-v1`
- CACHED window: 30 minutes
- after 30 minutes: STALE

The short freshness window reflects changing Calendar and Task state.

### HORIZON

- cache key: `latest_horizon`
- contract marker: `AUTH-1/get_latest_horizon/plain_text`
- CACHED window: 24 hours
- after 24 hours: STALE

The longer window reflects the daily executive-briefing lifecycle.

## Privacy behavior

Normal connectivity loss does not clear last-known-good state.

Explicit sign-out does clear:

- encrypted authentication material;
- dashboard Room cache;
- HORIZON Room cache;
- in-memory canonical read state.

This prevents private cached GPOS content from remaining visible after a deliberate sign-out.

## Versioning

- package: `com.cokkles.gpos`
- version: `0.2.0-dev`
- versionCode: `3`
- signing cache identity: `gpos-android-checkpoint-debug-signing-v1`

The package ID and signing identity are unchanged from the 0.1 signing baseline, so 0.2 is intended to install as an in-place upgrade over the signed 0.1 checkpoint.

## Validation gate

The checkpoint is acceptable only when CI passes:

- lint;
- JVM unit tests;
- dashboard mapping tests;
- HORIZON parser tests;
- Room/KSP generation;
- Compose compilation;
- app APK assembly;
- instrumentation APK assembly;
- APK signing fingerprint extraction;
- artifact upload.

## Stop conditions

Do not unilaterally:

- add or weaken AUTH-1 trusted audiences;
- change shared backend response semantics;
- treat Android cache as canonical authority;
- infer SENTINEL-FIN truth from HORIZON text;
- enable Calendar/Task writes before confirmation and retry semantics are validated;
- schedule background HORIZON/Gemini/PRISM generation;
- expose auth tokens in UI, logs, intents, deep links, analytics, or plaintext storage.

## Next candidate increment after 0.2 validation

0.3 should focus on explicit interaction contracts:

1. Calendar mutation contract and confirmation UX.
2. Task completion/editing contract.
3. Follow-up canonical feed and actions.
4. Idempotency/retry rules for safe mobile writes.
5. Notification/deep-link integration around those bounded actions.

No 0.3 mutation should begin until the relevant shared-backend contract is reviewed for Desktop/PWA compatibility.
