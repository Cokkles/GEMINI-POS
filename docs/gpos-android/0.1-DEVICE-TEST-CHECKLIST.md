# GPOS Android 0.1 — Device Test Checklist

Use this checklist with the validated 0.1 checkpoint APK.

## 1. Install / upgrade

1. Attempt to install the APK over the existing GPOS development build.
2. If Android reports an incompatible/signature installation error, uninstall the older pre-stable-signing GPOS APK once and install this checkpoint cleanly.
3. Future checkpoint builds should use the retained development signing identity established in 0.1.

## 2. Shell regression

Confirm the existing mobile shell remains smooth:

- Home
- Briefing
- Calendar
- Tasks
- More
- Follow-ups
- Finances
- Ask AEGIS
- System

No Windows PC or Windows Helper should be required.

## 3. Quote of the day

On Home:

- `Quote of the day` appears at the top.
- It loads immediately with no network delay.
- Reopening the app on the same calendar date keeps the same quote.

## 4. Themes

Go to `More -> System -> Appearance` and test:

- GPOS Light
- GPOS Dark
- Monokai
- Dracula
- Solarized Dark
- Nord

Check text/card/navigation contrast. Close and reopen the app and confirm the selected theme persists.

## 5. Public backend discovery

In System, check `Backend & authentication`.

Expected when online and the production endpoint is reachable:

- Backend: reachable
- AUTH-1 metadata shown
- backend version shown
- enforcement state shown
- allowlist configuration shown without exposing the allowlist itself

This public check should not expose Workspace-backed data.

## 6. Google sign-in

Tap `Sign in with Google`.

Expected successful path:

1. Android/Google native credential UI appears.
2. Choose an authorized account.
3. GPOS validates the returned Google ID token through AUTH-1.
4. System changes to `Authenticated` and displays bounded account identity only.
5. No raw token appears anywhere in the UI.

If Google reports a developer/configuration error before AUTH-1 is reached, record the exact error. The Android OAuth client registration may need package `com.cokkles.gpos` plus the signing SHA-1 produced with this checkpoint.

Do not weaken AUTH-1 validation to work around an OAuth registration issue.

## 7. Protected read check

When authenticated, tap `Refresh secure reads`.

Expected:

- health read succeeds;
- dashboard read succeeds;
- System shows a bounded status summary only;
- no mutation or generation is triggered.

## 8. Live HORIZON

After successful authentication:

- open Briefing;
- HORIZON should transition to `LIVE` if `get_latest_horizon` succeeds;
- the canonical `plain_text` briefing should render;
- the fetched time is displayed;
- Home should show a HORIZON preview tagged with its source.

## 9. HORIZON offline fallback

After at least one successful LIVE HORIZON fetch:

1. close the app;
2. disable connectivity or enter airplane mode;
3. reopen GPOS;
4. open Briefing.

Expected:

- the last-known-good HORIZON remains available from Room;
- source is `CACHED` while within freshness;
- eventually it becomes `STALE` after the defined freshness window rather than disappearing or pretending to be live;
- cached content is never labeled canonical authority.

## 10. Sign out

Tap `Sign out`.

Expected:

- local encrypted session material is cleared;
- UI returns to signed-out state;
- cached HORIZON may remain available as read-only last-known-good data;
- protected refresh requires sign-in again.

## 11. Current expected fixture surfaces

During 0.1, these remain intentionally fixture-backed until their production response shapes are validated:

- Calendar
- Tasks
- Follow-ups
- Finances

This is expected behavior, not a defect.

## Report back

The most useful test report is:

- install upgraded in place: yes/no
- selected theme + any contrast issue
- public backend reachable: yes/no
- Google sign-in result
- protected reads result
- HORIZON source shown: LIVE/CACHED/STALE/fixture
- any crash, freeze, or navigation issue
