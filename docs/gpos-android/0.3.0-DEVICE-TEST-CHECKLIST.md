# GPOS Android 0.3.0 — Device Test Checklist

## Purpose

0.3.0 is the first Android checkpoint that can intentionally mutate canonical Google Tasks, Google Calendar, and AEGIS server-notification state.

Treat this as a full reinstall/upgrade and authenticated device-validation checkpoint before broader 0.3 development continues.

Core rule:

> **READ AUTOMATICALLY. MUTATE EXPLICITLY.**

## Installation / identity

1. If a deterministic-signed 0.2.x build is installed, install 0.3.0 as an in-place upgrade.
2. If the phone still has an older ephemeral-signed build, uninstall that build once before installing the deterministic checkpoint APK.
3. Confirm Home reports `GPOS Android 0.3.0-dev`.
4. Confirm System still reports:
   - package `com.cokkles.gpos`
   - checkpoint SHA-1 `D2:A0:80:66:49:D0:00:B1:B8:4F:FF:45:A9:C6:DF:76:8D:FC:31:EA`

## Baseline regression smoke

Confirm existing 0.2 functionality remains intact:

- Home / Quote of the Day
- Briefing
- Calendar read view
- Tasks read view
- More navigation
- Finances
- Notifications
- Insights
- Follow-ups gated screen
- Ask AEGIS gated screen
- System / authentication
- all Appearance themes and theme persistence
- canonical LIVE/CACHED/STALE provenance
- sign-out cache clearing
- privacy-safe Android notifications

## Authentication prerequisite

Explicit mutation controls must only become operational with a currently authenticated AUTH-1 session.

Validate:

1. Sign in with the authorized Google account.
2. Confirm System reports the signed-in identity.
3. Refresh canonical reads and confirm Dashboard/Tasks/Calendar/Notifications are LIVE.

Then test the negative boundary:

1. Sign out.
2. Open Tasks, Calendar, and Notifications.
3. Confirm mutation actions cannot execute while signed out.
4. Restore cached data offline if available.
5. Confirm offline-restored/cached state remains read-only and does not enable mutation.

## Tasks — staging is local only

Use low-risk test tasks that you are comfortable completing.

1. Open **Tasks**.
2. Confirm active canonical Google Tasks are visible.
3. Stage one task for completion.
4. Before confirming, check Google Tasks independently and verify nothing changed yet.
5. Unstage it and verify nothing changed.
6. Stage one or more tasks again.
7. Confirm the UI reports the staged count and gives a separate completion action.
8. Cancel/back out before confirmation once and verify nothing changed.

### Canonical-ID safety

If any dashboard task lacks a proven backend Google Task ID, it may still render but must not be presented as safely mutable/stageable.

Do not accept any behavior where a synthesized/display-only ID is sent as a Google Task ID.

## Tasks — explicit completion and verification

1. Stage a disposable/appropriate test task.
2. Explicitly confirm completion.
3. Verify Google Tasks independently.
4. Verify GPOS refreshes canonical state and removes the completed task only after the live canonical read confirms it is gone.
5. Confirm no duplicate command occurs if you tap elsewhere, rotate, navigate away, or reopen the screen.

### Failure/uncertainty behavior

If practical, test a network interruption after staging and before submission:

- no mutation should be claimed as successful without confirmation;
- selected/staged task IDs should remain available for review when completion cannot be confirmed;
- Android must not automatically retry `mark_done` after an uncertain failure.

If the server responds but a selected task remains in the fresh canonical dashboard, GPOS should report it as unconfirmed and preserve it rather than pretending it completed.

## Calendar — resolve without creation

Use a harmless test event.

1. Open **Calendar**.
2. Enter a natural-language event description, for example a clearly labeled temporary test event.
3. Tap the resolve/preview action.
4. Confirm a structured proposal appears with title/start/end and optional location/description.
5. Check Google Calendar independently **before** tapping Add.
6. Verify no event was created merely by resolving the text.
7. Cancel/reset the proposal once and verify no event is created.

## Calendar — explicit create

1. Resolve another harmless test event.
2. Carefully review title, date, start, end, location and description.
3. Tap **Add to Calendar** once.
4. Verify the event appears in Google Calendar.
5. Verify GPOS refreshes the canonical Calendar view.
6. Confirm navigation/recomposition does not submit the same proposal again.

Important:

- 0.3.0 does not expose Calendar edit/delete.
- If the create result is uncertain because of a network interruption, do not repeatedly tap Add without checking Google Calendar first; non-idempotent mutation is intentionally not auto-retried.

## Notifications — opening is not acknowledgement

Use an existing non-critical test/appropriate server notification if one is available.

1. Open **More → Notifications**.
2. Open/navigate around the screen.
3. Leave and return.
4. Verify the server notification remains unacknowledged.
5. If an Android notification deep-link is available, tap it and verify simply opening GPOS does not acknowledge the server alert.

## Notifications — explicit acknowledgement

1. Choose one appropriate server notification.
2. Tap **Acknowledge** once.
3. Verify it disappears from the active/unacknowledged canonical list after refresh.
4. Confirm unrelated notifications remain unchanged.

If the server reports that the notification ID is not found, Android must not display a successful acknowledgement state.

## Notification runtime permission

1. Disable GPOS notification permission in Android Settings.
2. Trigger/allow a background refresh path if possible.
3. Confirm GPOS does not crash when it cannot post a notification.
4. Re-enable permission.
5. Confirm a newly observed critical alert, when available, can produce the generic privacy-safe notification.
6. Confirm lock-screen text does not expose the private server alert content.

## Background worker mutation prohibition

Leave the app installed and authenticated long enough for WorkManager operation.

The background worker may read:

- dashboard
- recent finance
- notifications
- stale/missing HORIZON

It must never automatically:

- complete a Google Task
- create/edit/delete Calendar events
- acknowledge a server notification
- generate HORIZON
- invoke Gemini generation
- invoke PRISM
- refresh RSS/Intelligence
- mutate finance

## Offline test

After successful live refresh:

1. Close GPOS.
2. Disable network connectivity.
3. Reopen GPOS.
4. Verify cached canonical content remains visibly CACHED/STALE as appropriate.
5. Confirm Tasks, Calendar creation, and notification acknowledgement cannot produce fake success.
6. Re-enable network and perform an explicit canonical refresh.

## Sign-out privacy test

1. Sign out after live private data has been cached.
2. Confirm private Dashboard/HORIZON/Finance/Notifications content is cleared.
3. Relaunch while signed out.
4. Confirm private content does not reappear.
5. Confirm no staged mutation is silently submitted during sign-out or the next launch.

## Gated areas must remain gated

Confirm no new production writes were accidentally exposed for:

- Follow-ups
- Ask AEGIS
- Finances
- HORIZON generation
- Tasks create/edit/delete
- Calendar edit/delete

## Report back

For each issue, capture:

- screen/action
- expected result
- actual result
- whether canonical Google/AEGIS state changed
- whether the app was LIVE, CACHED, STALE, or offline
- exact error/diagnostic text
- screenshot if visual behavior is involved

A 0.3.0 device-validation PASS requires both positive mutation tests and the negative safety tests above.
