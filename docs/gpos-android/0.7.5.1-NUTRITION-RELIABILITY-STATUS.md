# AEGIS Android 0.7.5.1 — Nutrition Reliability

## Outcome

Android 0.7.5.1 is the client half of the Apps Script 2.8.1 nutrition reliability checkpoint.
It remains compatible with backend 2.8.0 by sending both the additive structured action and the
legacy `/calories` message.

## Android changes

- Every meal carries one stable Capture ID through retries.
- Meal requests identify `GPOS_ANDROID`, client version, requested nutrition contract, and source policy.
- Structured confirmation metadata includes confidence, lookup depth, and deduplication status.
- A queued capture changes from the stale authorization message to `Submitting to AEGIS…` as soon as work begins.
- Certified not-started capacity failures retry after 60 and 120 seconds, then expose a manual retry.
- The UI queue remains local, encrypted, durable across app restart, and erased on explicit logout.
- Version is `0.7.5.1` / version code `20` using the established checkpoint certificate.

## Backend 2.8.1 candidate

- `shared-backend/patches/2.8.1-nutrition-reliability.gs` implements the new contract.
- `shared-backend/patches/2.8.1-ROUTER-INSTALL.md` records the exact additive installation.
- Legacy sheet columns A:J remain unchanged. New provenance/nutrition fields occupy K:X.
- The full authoritative 2.8.0 `Code.gs` is still live-owned and must not be reconstructed from an older source.
- Backend 2.8.1 is not considered deployed until the registry and runtime gates are completed.

## Compatibility

- Windows/PWA legacy `/calories`: preserved.
- Android on backend 2.8.0: preserved legacy behavior, without unsafe automatic retries.
- Android on backend 2.8.1: structured idempotent capture and safe bounded retries.
- HORIZON/KINETIC reads of calories, protein, carbohydrates, fat, and sodium from A:I: preserved.
