## Production runtime inspection — critical mismatch

A direct inspection of the currently versioned AEGIS Apps Script source in `Cokkles/aegis-itinerary-project` revealed that the checked-in `main/Code.gs` still contains executable legacy and pre-V2 HORIZON behavior:

- `doGet()` still serves `getHorizonData` / `getSummary` by reading `horizon_data.json`.
- `mark_done` still calls `pruneHorizonJsonFile()`.
- the `/horizon` / `refresh_briefing` / `horizon_sync` route still calls `refreshHorizonDataFeed()` after `runHorizonPipeline()`.
- `pruneHorizonJsonFile()` and `refreshHorizonDataFeed()` still contain live Drive read/write implementations rather than kill guards.
- `refreshHorizonDataFeed()` still reads raw nutrition data via `getTodayCaloriesFromSheet()` and writes legacy JSON state.
- `runHorizonPipelineUnsafe()` constructs a Gemini prompt primarily from Calendar and Tasks and asks Gemini to generate KINETIC, SENTINEL-FIN, Gmail, “Things to Consider,” and newspaper sections without supplying the approved V2 bounded contracts.

This source state directly conflicts with the previously reported legacy-eradication state and with the frozen V2.5 cutover requirements.

### Interpretation

The repository copy of AEGIS Apps Script is either:

1. an active source that has not actually received the reported remediation; or
2. a stale mirror that is not identical to the currently deployed Apps Script runtime.

Either case blocks a defensible production cutover claim until the authoritative deployed Apps Script project is identified and reconciled.

## Exact blockers

V2.5 production cutover is blocked by two concrete runtime gaps:

1. **No deployable live producer/service is currently identified for `KINETIC_TO_HORIZON_V2` and `SPARK_TO_HORIZON_V2`.** The validated Python producers exist in GEMINI-POS, but the current Apps Script route cannot call repository Python code directly.
2. **The available tooling can edit GitHub and Workspace documents but cannot deploy or update the authoritative Google Apps Script project/deployment.** Therefore a source-control patch alone cannot prove production cutover.

A third verification item is required because of the source/runtime discrepancy:

3. **Identify whether `Cokkles/aegis-itinerary-project/main/Code.gs` is the actual deployed source.** If not, the deployed Apps Script code must be exported/reconciled before changes are made.

## Rollback point

The permitted rollback point is the immediately prior working HORIZON Apps Script deployment/version. Rollback must never reactivate `horizon_data.json`, `refreshHorizonDataFeed()`, `pruneHorizonJsonFile()`, or any retired JSON route. Before deployment, the authoritative Apps Script deployment/version ID must be recorded so rollback is deterministic.

## Cutover decision

**DO NOT CLAIM PRODUCTION CUTOVER YET.**

The repository-native V2.5 consumer is implemented and CI-valid, but the live execution target cannot yet be proven to consume it. The currently visible Apps Script source also contains contradictory legacy executable paths.

This is intentional fail-closed behavior: repository implementation does not equal production deployment, and a stale or conflicting source mirror is not accepted as evidence of runtime state.
