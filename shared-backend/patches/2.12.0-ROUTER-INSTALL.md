# Apps Script 2.12.0 canonical nutrition rows

Backend 2.12.0 builds on the 2.11.1 nightly reliability controller. It routes
all new and reconciled nutrition rows through one deterministic sheet renderer.
It preserves Calendar/Task 2.11.0 behavior, Android and Windows routes,
nutrition A:X, AUTH-1, device sessions, HORIZON, and the 2.8.4.1 rollback.

Installation does not rewrite historical nutrition rows.

## Install without historical mutation

Run:

```text
installAegisNutritionNightlyReliabilityV2111()
installAegisNutritionSheetNormalizationV2120()
```

The second result must include:

```text
historical_rows_changed: 0
preview_required_before_cleanup: true
```

Confirm `getInstalledAegisTriggers()` contains exactly one daily
`runAegisNutritionNightlyControllerV2111` trigger and one daily
`runAegisNutritionNightlyWatchdogV2111` trigger. A retry trigger should exist
only while a transient provider retry is pending.

Edit the existing web-app deployment, choose **New version**, and retain the
existing deployment ID and URL. Confirm `auth_config.backend_version` is
`2.12.0` and both new nutrition capabilities are `true` before client smoke
tests.

## Historical cleanup (optional and review-gated)

First run:

```text
previewAegisNutritionSheetNormalizationV2120(200)
```

Review every proposed item/portion pair. Nothing is changed by the preview.
Apply only approved, explicit sheet row numbers, for example:

```text
applyAegisNutritionSheetNormalizationV2120([42, 57, 61])
```

Each call accepts at most 100 rows and records the before/after values in the
hidden `_AEGIS_NUTRITION_NORMALIZATION_AUDIT_V1` sheet. The cleanup changes
only columns C, D, W, and X; it does not recalculate nutrition values.

## Runtime acceptance

1. Submit one new capture with a quantity attached to the item text.
2. Confirm `Food Item` contains identity only and `Portion` contains the amount.
3. Confirm status polling and the Android/Windows reads still return the row.
4. Run the nightly controller through its scheduled path.
5. If the provider returns a controlled transient failure, confirm
   `retry_scheduled: true`, a non-null `next_attempt_at`, and exactly one retry
   trigger.
6. After the retry succeeds, confirm the capture is no longer pending and the
   item/portion layout remains canonical.

Do not claim 2.12.0 deployed until Apps Script runtime tests, the new web-app
version, capability checks, and cross-client smoke tests all pass.
