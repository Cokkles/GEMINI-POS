# Apps Script 2.10.0 KINETIC identity and serving hardening

Backend 2.10.0 completes the first three approved nutrition-hardening phases on
top of the 2.9.0 nightly architecture:

1. product identity and category protection;
2. safe reuse of trusted prior foods;
3. deterministic, product-specific serving conversion.

Capture-time Gemini calls remain disabled. Apps Script remains the system of
record, and the existing nightly KINETIC batch remains the only AI nutrition
review lane.

## What changes

### Identity protection

- Branded input must retain its known brand.
- A candidate cannot cross known food categories.
- Generic keyword overlap cannot override a specific product.
- `Chobani Coffee Yogurt` cannot become `Black coffee`.
- A mismatched nightly item becomes `NEEDS_REVIEW`; it does not overwrite
  the provisional nutrition row or prevent unrelated captures from being
  reviewed.
- Unsafe exact entries in the old evidence catalog are ignored rather than
  reused.

### Trusted food reuse

- Trusted food identity is keyed separately from amount/portion.
- A trusted prior food can be reused for a different amount without new
  research.
- Exact aliases and high-overlap candidates still require brand and category
  consistency.
- Only accepted medium/high-confidence nightly results backed by medium/high
  source authority enter the trusted catalog automatically.
- Existing history can be imported, but only rows already marked
  `CONFIRMED`, `VERIFIED`, or `ADJUSTED` with medium/high confidence and
  source authority are trusted automatically. Ambiguous legacy rows are
  skipped instead of silently becoming authoritative.

### Deterministic serving conversion

- Local arithmetic supports serving, package, count, g, kg, oz, lb, ml, L,
  fl oz, cup, tbsp, and tsp.
- Count, mass, volume, and package relationships must come from the exact
  product's trusted serving definition.
- Cross-dimension conversion is forbidden without that product-specific
  relationship. A generic tablespoon is never assigned a universal weight.
- Grams or milliliters are never fabricated.

## Pre-deployment tests

Run these functions in Apps Script in order:

1. `testAegisNutritionProviderRoutingV284()`
2. `testAegisNutritionMultiItemIntegrityV2841()`
3. `testAegisNutritionNightlyContractV290()`
4. `testAegisNutritionIdentityServingV2100()`
5. `testAegisNutritionQueueV282()`
6. `testAegisNutritionIdempotencyV282()`
7. `testAegisNutritionStatusLifecycleV282()`
8. `testAegisDeviceSessionsV283()`

Expected `testAegisNutritionIdentityServingV2100()` result:

- status: `PASS`
- Chobani → black coffee rejected: `true`
- four Fig Newton cookies: `1` serving
- one tablespoon using a 2 tbsp product serving: `0.5`
- 16 g using a 32 g product serving: `0.5`

These contract tests do not make a live Gemini request.

## Initialize the catalog

After pre-deployment tests pass, run:

```text
installAegisNutritionHardeningV2100()
```

This creates and hides the trusted-food sheet. It does not change nutrition
rows.

Then run once:

```text
importAegisTrustedNutritionHistoryV2100()
```

Review the returned `imported` and `skipped` counts. Skipped history is
intentional: unverified or weakly sourced legacy values remain available in the
nutrition log but do not become automatic lookup authority.

## Mandatory controlled regression stop

Use new capture IDs for every test.

| Input | Required result |
|---|---|
| `Chobani Coffee Yogurt` | Must remain a Chobani yogurt product; must never become black coffee |
| `12 fl oz black coffee` | May resolve as black coffee |
| `4 Fig Newton cookies` | 1 product-specific serving; 200 kcal using the current trusted fixture |
| `2 Fig Newton cookies` | 0.5 serving; 100 kcal |
| `8 Fig Newton cookies` | 2 servings; 400 kcal |
| `29 g Fig Newton cookies` | 0.5 serving; 100 kcal |
| `1 tbsp peanut butter` after a trusted `2 tbsp (32 g)` record | 0.5 serving |
| `16 g peanut butter` using that same record | 0.5 serving |
| `1 tbsp` of an unrelated food without a density/serving relationship | No invented grams; provisional/review path |
| Previously trusted food with a changed amount | Reuse the same product identity and scale locally |
| Same keyword but different category | No trusted match; preserve input and review |

Also repeat the 2.9.0 five-item fixture and confirm:

- exactly five rows;
- no item combination or reordering;
- capture returns immediately without Gemini;
- nightly review handles every capture and item;
- an identity/portion mismatch affects only that capture and becomes
  `NEEDS_REVIEW`;
- rerunning a completed batch produces `NO_PENDING_ITEMS`;
- no duplicate nutrition rows or trusted-food records are created.

Stop after this controlled backend test and report results before Phase 4
display normalization or any Android package work begins.
