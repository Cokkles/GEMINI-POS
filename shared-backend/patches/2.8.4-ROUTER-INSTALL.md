# Apps Script 2.8.4 nutrition provider hardening installation

This is an additive update over the installed 2.8.3 backend. It preserves all
existing routes, the legacy `/calories` response, nutrition columns A:X, device
sessions, and the Windows/PWA/Android shared contract.

## Files in the Apps Script project

Keep these as separate script files. Do not merge them together.

| Apps Script file | Repository source | Action |
|---|---|---|
| `Code.gs` | `shared-backend/Code.gs` | Replace the full contents |
| `NutritionReliability281.gs` | Existing installed file | Leave unchanged |
| `NutritionQueue282.gs` | `shared-backend/patches/2.8.2-durable-nutrition-queue.gs` | Replace the full contents; do not add a duplicate |
| `DeviceSessions283.gs` | Existing installed file | Leave unchanged |
| `NutritionProviderReliability284.gs` | `shared-backend/patches/2.8.4-nutrition-provider-hardening.gs` | Add as a new script file |

Apps Script filenames can differ, but there must be exactly one copy of each
function. A duplicate old queue module will cause duplicate-function ambiguity.

## Optional explicit model properties

The module has safe defaults, so these properties are not required. To pin the
models explicitly, set these in Project Settings > Script Properties:

- `AEGIS_NUTRITION_SIMPLE_MODEL` = `gemini-3.5-flash-lite`
- `AEGIS_NUTRITION_GROUNDED_MODEL` = `gemini-3.6-flash`

The existing `GEMINI_API_KEY`, `GEMINI_MODEL`, authentication, and allowlist
properties remain unchanged.

## Save and validate before deployment

Run these functions in order:

1. `testAegisNutritionProviderRoutingV284()` — no Gemini call; verifies the
   known-food path, simple/grounded routing, and quota parsing.
2. `testAegisNutritionSimpleProviderV284()` — one ungrounded Flash-Lite call;
   verifies that the lower-cost/high-throughput model is available.
3. `testAegisNutritionQueueV282()` — verifies deterministic resolution,
   zero-row rejection, and retry scheduling.
4. `testAegisNutritionIdempotencyV282()` — writes and automatically removes a
   one-row fixture while verifying duplicate protection.
5. `testAegisNutritionStatusLifecycleV282()` — writes and automatically removes
   a queue fixture.
6. `testAegisDeviceSessionsV283()` — verifies the existing device-session layer.

If a prior test opened a provider circuit, run
`resetAegisNutritionProviderCircuitsV284()` once, then repeat only the failed
provider test.

## Deploy and verify

1. Deploy > Manage deployments > Edit the active web app.
2. Select **New version**, then deploy. Do not create a different web-app URL.
3. Verify `auth_config.backend_version` is `2.8.4`.
4. Verify capabilities include:
   - `nutrition_provider_routing_v1: true`
   - `nutrition_quota_diagnostics_v1: true`
   - `nutrition_circuit_breaker_v1: true`
   - all existing 2.8.3 nutrition and device-session capabilities.
5. Run `processAegisNutritionQueueV282()` once to immediately reprocess safely
   queued captures, including the existing Fig Newton capture.
6. In Android, tap **Check status**. The Fig Newton capture should become
   `CONFIRMED` without creating a duplicate row.
7. Capture a new simple food, then a restaurant meal. The simple food should use
   the non-search lane; the restaurant meal may use grounded lookup or a clearly
   labeled conservative fallback.
8. Submit the same capture ID twice and confirm exactly one nutrition row set.
9. Run a legacy PWA `/calories` check and basic Windows/PWA/Android smoke tests.

## Rollback

Rollback is the last verified 2.8.3 deployment version. Re-select that deployment
version; no sheet migration or column removal is required.

## Secondary-provider decision gate

Do not add another AI provider merely because one isolated 429 occurs. Start a
secondary-provider assessment if either condition is observed after 2.8.4:

- the simple Flash-Lite lane records repeated capacity failures across two test
  windows, or
- captures remain queued for more than six hours despite the tiered routing and
  circuit breaker.

The assessment should compare structured JSON reliability, nutrition/search
quality, quotas, price, privacy, and Apps Script compatibility before a provider
is selected.
