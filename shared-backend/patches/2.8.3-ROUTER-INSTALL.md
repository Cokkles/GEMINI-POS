# Apps Script 2.8.3 device-session installation

This checkpoint layers durable device authentication on the undeployed 2.8.2
nutrition queue. Keep these four files separate in the Apps Script project:

- Code.gs
- NutritionReliability281.gs
- NutritionQueue282.gs
- DeviceSessions283.gs

Do not deploy these snippets against a reconstructed or partial router. Merge them
into the exact authoritative 2.8.1 Code.gs.

## Contract

- Google AUTH-1 remains the only initial identity proof.
- A successful auth_login may issue AEGIS_DEVICE_SESSION_V1.
- Device sessions last 30 days and roll forward during auth_session validation
  inside the final seven days.
- The Android installation ID names one revocable device session; it is not a secret.
- Existing Google ID tokens remain accepted for Windows, PWA, older Android, and rollback.
- Credential/session tokens remain in the existing auth_token payload field.

## Required authoritative-router merge

1. Change the deployment candidate version to 2.8.3.
2. Advertise device_session_v1: true and interactive_auth_background_forbidden_v1: true.
3. Run installAegisDeviceSessionsV283() once.
4. After the existing auth_login path has successfully verified Google AUTH-1,
   its allowlist, and server-derived scopes, wrap its successful response:

    loginResponse = attachAegisDeviceSessionV283_(
      loginResponse,
      verifiedIdentity,
      verifiedScopes,
      contents
    );

verifiedIdentity and verifiedScopes must come from the existing server verifier.
Never copy identity or scopes from request fields.

5. At the beginning of the existing protected authorization function, before Google
   token verification, detect the prefixed token:

    var deviceSession = tryAuthorizeAegisDeviceSessionV283_(contents, requiredScope);
    if (deviceSession) {
      // Return the same authorization-success shape already returned by this function,
      // populated from deviceSession.user and deviceSession.scopes.
    }

If a prefixed device session throws an error, return AEGIS_AUTH_FAILED; never pass
it to Google verification as a fallback.

6. In auth_session, route prefixed tokens through
   handleAegisDeviceSessionValidationV283_(contents). This response may contain a
   renewed token; Android stores it atomically.
7. In auth_logout, call handleAegisDeviceSessionLogoutV283_(contents) first and
   return its non-null response. Legacy Google-token logout remains unchanged.

The exact success-shape merge in step 5 cannot be finalized without the authoritative
Code.gs, because the current repositories intentionally do not contain that source.

## Pre-deployment tests

Run, in order:

1. testAegisNutritionInputV281()
2. testAegisNutritionValidationV281()
3. testAegisNutritionQueueV282()
4. testAegisNutritionStatusLifecycleV282()
5. testAegisNutritionIdempotencyV282()
6. testAegisDeviceSessionsV283()
7. installAegisNutritionQueueV282()
8. installAegisDeviceSessionsV283()

Then create a new deployment version and verify:

- auth_config.backend_version equals 2.8.3
- all 2.8.1 and 2.8.2 nutrition capabilities remain true
- device_session_v1 is true
- interactive_auth_background_forbidden_v1 is true
- initial Android Google login returns session.type AEGIS_DEVICE_SESSION
- auth_session accepts that token after the original Google ID token expires
- logout revokes that exact session
- legacy Google-token authentication still works
- Windows, PWA, Android, HORIZON, Tasks, Calendar, Finance, RSS, and nutrition smoke tests pass

## Rollback

Select the previous validated 2.8.1 deployment. Android 0.7.6.1 retains the legacy
Google-token response fallback but never launches Google UI automatically; an expired
legacy token therefore shows a passive reconnect requirement. Preserve the device-session
registry property for diagnosis. Remove it only after rollback analysis.
